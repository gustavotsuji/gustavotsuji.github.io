機能を完成させ、プルリクエストを作成し、パイプラインのグリーンチェックを待っている間に、CI が失敗した経験はありませんか？ 10 分後、CI が失敗する — 原因は単純な lint エラーや Sonar の指摘かもしれません。これらはローカルで数秒で修正可能なはずです。

このような失敗は、CI の実行回数を増やしコストを押し上げ、余分な計算リソースを浪費します。さらに、些細な修正ごとに再度 push する必要があり、パイプラインが再起動し、既に行われたコードレビューの承認が無効になることもあります。

この記事では、Husky を使ってこれらのチェックを開発者環境に持ち込み（Shift-Left）、チームの生産性を損なわないカスタマイズ可能な設定戦略を提案します。

## "Shift-Left" の概念

基本的なアイデアはシンプルです。すべてのステップをローカルで実行できれば、成功の可能性が高まり、CI での無駄な待ち時間を避けられます。Shift-Left は Lint、テスト、Sonar、セキュリティなどの品質チェックをサーバに到達する前に開発者のマシンで実行することを意味します。

## 守護者: Husky

Husky を使い、Git イベント（Git Hooks）によって自動でスクリプトを実行します。Husky はゲートキーパーとして機能し、チェックが失敗した場合、git の操作（commit や push）を即座に中止します。

戦略は主に二つの段階に分かれます:

1. **Pre-commit:** ステージされたファイルに対してのみフォーマッタやリンターを実行します。

2. **Pre-push:** リモートに送る前に重いテストやセキュリティチェックを実行します。

## 開発者ごとのカスタマイズ

ローカルフック採用における懸念のひとつはスピードです。"毎回 push するたびに Sonar を回すの？" 答えは: ユーザー次第です。

この問題を解決するため、リポジトリのルートに開発者が作る（.gitignore に含める）未追跡の設定ファイルを用意しました（例: `.husky.user.config`）。この中でブール変数を定義し、チェックを有効/無効にできます。

```bash
# .husky.user.config
export HUSKY_RUN_LINT=true
export HUSKY_RUN_GITLEAKS=true
export HUSKY_RUN_UNIT_TESTS=true
export HUSKY_RUN_TRIVY_SCAN=true
export HUSKY_RUN_SONAR_SCAN=false
```

スクリプトはこのファイルを読み取り、変数が `false` か存在しない場合は該当ステップをスキップします。

## 検証内容

この構成により、コードがマシンを出る前に複数の品質レイヤーを確保できます。

### Pre-commit:

- Lint & Prettier
- GitLeaks
- Dockerfile の検証（変更があればビルドを試す）

### Pre-push:

- ユニットテスト
- Trivy（脆弱性スキャン）
- NPM Audit

### SonarQube 統合（ローカル）

`HUSKY_RUN_SONAR_SCAN=true` の場合:

1. Docker 経由で SonarQube コンテナが動作しているかチェックし、なければ起動。
2. プロジェクトの存在を確認し、なければ API 経由で作成。
3. `sonar-scanner` を実行。
4. Quality Gate を API で参照し、ERROR なら push を中止します。

## 結論

`--no-verify` でチェックをスキップすることは可能ですが（推奨されません）、このアーキテクチャは開発者を支援することを目的としています。

ローカルで選択的に検証を実行することで CI の待ち時間を大幅に短縮し、Actions の消費を削減し、些細なパイプライン破損を回避できます。
