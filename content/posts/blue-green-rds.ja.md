# ゼロダウンタイムとクラウドコスト削減: RDSのBlue/Greenデプロイで予算を救った方法

TL;DR

- AWS RDS の Blue/Green Deployment を使い、PostgreSQL の移行とダウンサイジングをほぼ無停止で実施しました。
- 結果: 月額約 $425 のコスト削減（試算）；前提条件: トラフィックの低い時間帯、スナップショット、整合性テスト。
- 事前要件: 手動スナップショット、拡張機能の互換性確認（例: PostGIS）、DNS TTL と接続プールの再接続戦略の確認。

本番データベースの運用担当なら、重大な保守作業で感じるあの緊張を誰もが知っています。最近、私たちは一般的だが難しい課題に直面しました: 数百件/分のトランザクションを処理する重要な PostgreSQL のアップグレードとリサイズを、ユーザー体験を損なわずに実行する必要がありました。

状況はこうでした: 私たちのデータベース（通称 _taffarel_）は過剰にプロビジョニングされていました。分析の結果、`r6g.4xlarge` から `x2g.2xlarge` に移行すれば CPU を半分にでき、**月額 $425 の節約**になることがわかりました。

また、AWS 上の PostgreSQL のサポート終了（EOL）にも直面していました。古いバージョンを維持するには延長サポート（約 **$413/月**）が必要で、一時的な対処に過ぎません。

重要な質問: **本番データベースでどうやってゼロダウンタイムでこの移行を実行するか？**

## 従来の手法と Blue/Green の比較

手動で行うアプローチは手間とリスクが大きいです。リードレプリカを作り、昇格・アップグレード・ダウンサイジングを行い、アプリケーションを停止してエンドポイントを切り替え……問題が起きないことを祈るしかありません。

そこで私たちは **AWS RDS Blue/Green Deployment** を選びました。

### RDS の Blue/Green とは

アプリケーションのデプロイとは異なり、RDS の Blue/Green は本番（Blue）の正確な同期コピーとしてステージング（Green）を作成します。

この機能はデータだけでなく接続、設定、ログ、パラメータも複製します。これにより、Green 上でエンジンのアップグレードやスキーマ変更など大きな変更を実施し、本番を触らずに検証できます。

## スイッチオーバーの仕組み

変更を適用して Green の動作確認を行ったら、AWS コンソール（または CLI/API）でスイッチオーバーを実行します。

このプロセスは安全でほぼ瞬時に行われ、次のことを保証します:

- エンドユーザーにとって**認識できるダウンタイムがほぼない**。

- **迅速なロールバック**: Green に問題があれば Blue に戻せる。

- **影響の最小化**: 本番データで検証できるが本番には影響を与えない。

## 注意点・落とし穴

注意すべきポイントは次の通りです:

1. **一時的なコスト増加**: 同期中は Blue と Green の両方のインスタンス分の料金が発生します。

2. **互換性の問題**: 一部の拡張は互換性がない場合があり、開始前に無効化が必要になることがあります。

3. **エンジン対応**: すべてのバージョンやデータベースエンジンがこの機能をサポートしているわけではありません。

## デプロイ前チェックリスト

- 変更前に手動スナップショット／バックアップを取得する。
- 拡張機能や依存関係の互換性を確認する（例: PostGIS, citext）。
- トラフィックの低いウィンドウを確保し、影響を受けるチームに通知する。
- DNS の TTL を確認し、クライアント／プール（pgbouncer, RDS Proxy）の再接続計画を立てる。
- Blue/Green デプロイを作成・管理するための IAM 権限を確認する。
- CloudWatch（レイテンシ、エラー、リプリケーション遅延）と一時的なアラームを設定する。
- 一時的に発生するコスト（インスタンスが2台稼働する期間）を算出し、必要なら予算承認を得る。
- ポストスイッチオーバー検証のためのスモークテストと整合性チェック用クエリを準備する。

## 手順の概要

コンソール上の流れは次のとおりです:

1. 対象のインスタンスを選択し、**Actions > Create Blue/Green Deployment** を選ぶ。

2. 新しい Green インスタンスの設定を定義する（ここでエンジンのバージョンやインスタンスファミリを選び、コスト削減を図る）。

3. 作成と同期が完了するのを待つ。Blue は _Available_、Green は _Creating_ のステータスになります。

4. Green のエンドポイントでテストを実行する。

5. 準備ができたらデプロイメントを選択して **Switch over** をクリックする。

6. 成功を確認したら古いインスタンスを削除して節約を確定する。

Blue/Green の導入により、リスクの高い重要な保守作業が安全で再現可能な手順へと変わり、アプリケーション性能とインフラコストの両方を守ることができました。
