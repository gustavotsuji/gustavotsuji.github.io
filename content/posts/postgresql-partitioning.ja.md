大量のデータを扱うエンジニアなら誰もが知っていることですが、ある時点でテーブルのサイズがその代償を求め始めます。クエリは遅くなり、インデックスは巨大化し、メンテナンス作業がデータベース全体に過負荷をかけるようになります。

最近、私たちのチームでも巨大なテーブルに起因するパフォーマンスとコストの問題に直面しました。特に、巨大なテーブルに対する `VACUUM` のリソース消費が激しく、重要なプロセスで極端な遅延やタイムアウトが発生していました。

これを緩和するために採用した解決策が **テーブルパーティショニング（Table Partitioning）** です。これは、リソースを最適化するためにテーブルをより小さな部分に分割する手法です。この記事では、この技術の概要、PostgreSQLでの動作、そして使用すべき（あるいはすべきでない）ケースについて探ります。さらに、`pg_cron` や `pg_partman` などのツールを使用して、パーティションの作成や古いデータの削除を自動化する方法についても解説します。

## テーブルパーティショニングとは？

パーティショニングとは、大きなテーブルを「パーティション」と呼ばれる小さな部分に分割する技術です。

この仕組みの素晴らしい点は、その透明性にあります。アプリケーションやエンドユーザーにとっては、これらのパーツは依然として単一のテーブルのように振る舞います。しかし物理的には、各パーティションは（日付、ステータス、IDなどの基準で定義された）データのサブセットのみを格納します。

PostgreSQLは、定義されたルールに基づいて、どのパーティションにデータを保存するか、あるいはどこからデータを取得するかを自動的に判断する責任を負います。

## なぜ使用するのか？

巨大なテーブルの問題を解決するだけでなく、パーティショニングは構造的に重要なメリットをもたらします：

1. **読み取りパフォーマンス:** 特にパーティショニングキー（分割の基準となる列）を使用した読み取りやフィルタリングにおいて、巨大なテーブルのパフォーマンスが大幅に向上します。
2. **メンテナンスとクリーンアップ:** 何百万行もの古いデータを削除することを想像してみてください。パーティショニングを使用すれば、コストのかかる `DELETE` 処理の代わりに `DROP` でパーティションごと削除できるため、データのアーカイブやクリーンアップが容易になります。
3. **インデックスの最適化:** 巨大なモノリシックなインデックスの代わりに、より小さく特定の範囲に限定されたインデックスを持つことになるため、メンテナンス性が向上します。
4. **リソース使用率:** ディスク容量の使用効率が改善され、`autovacuum` の実行がはるかに効率的になります。

## パーティショニングの種類

PostgreSQLは主に3つのネイティブ戦略を提供しています：

- **RANGE（範囲）:** 日付のように、データが範囲で整理されている場合に理想的です。（例：年/月で分割されたイベントテーブル）
- **LIST（リスト）:** ステータスや地域など、データが固定のカテゴリを持つ場合に使用されます。
- **HASH（ハッシュ）:** 特定の論理的な順序なしに、データを均等に分散させたい場合に使用します。

## 実践的な動作

PostgreSQLでの実装は宣言的です。以下は、イベントを保存するために日付（RANGE）でパーティション化されたテーブルを作成する例です：

```sql
-- 1. 親テーブル（パーティション化されたテーブル）の作成
CREATE TABLE eventos (
    id SERIAL,
    data_evento DATE NOT NULL,
    descricao TEXT,
    PRIMARY KEY (id, data_evento)
) PARTITION BY RANGE (data_evento);

-- 2. 特定のパーティションの作成
CREATE TABLE eventos_2023 PARTITION OF eventos
    FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');

CREATE TABLE eventos_2024 PARTITION OF eventos
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');

```

`SELECT * FROM eventos WHERE data_evento >= '2024-01-01';` のようなクエリを実行すると、データベースは自動的に「プルーニング（剪定）」を行い、関連するパーティションにのみアクセスします。

## 一般的なユースケース

パーティショニングは以下のようなシナリオで理想的です：

- 日付で整理されたログ
- 履歴イベントデータ
- 会計ファイル、請求書、トランザクション
- カテゴリ別のジョブ、通知、ステータス

## 注意点と使用すべきでないケース

パーティショニングには計画が必要です。考慮すべき運用上の複雑さが存在します：

1. **手動管理:** パーティションは通常、手動で作成するか、`pg_partman` のようなツールで管理する必要があります。
2. **インデックスとキー:** 最新のPostgreSQLはインデックスを自動的に伝播しますが、**主キー（Primary Keys）** や **一意制約（Unique Constraints）** の定義にはパーティションキーを含める必要があり、データモデリングに影響を与えます。
3. **制約事項:** パーティションテーブル上の _トリガー_、_制約_、_外部キー_ にはいくつかの制限があります。
4. **結合（Join）のパフォーマンス:** 多数のパーティションを巻き込む操作は、適切に計画されていない場合、遅くなる可能性があります。

**特に、以下の場合にはパーティショニングを避けてください：**

- テーブルが小～中規模である（実質的なメリットが得られない）。
- 読み取り量は多いが、クエリのフィルタ条件がパーティション列を **使用していない**。
- 計画的なメンテナンス運用（DROPやアーカイブのルーチンなど）がない。

## パーティショニングを自動化するには？

手動でのパーティション作成は運用上のリスクです。例えば、翌月分のパーティション作成を忘れると、特定のトラブルを引き起こす可能性があります。「フォールバック」パーティション（通常は default として定義される）が存在する場合、宛先が見つからないデータはすべてそこに送られてしまいます。

これを堅牢に解決するための標準的な組み合わせは、以下の2つの拡張機能を使用することです：

1. **pg_partman:** 新しいパーティションの自動作成と古いパーティションの破棄を管理します。
2. **pg_cron:** データベース _内部_ で実行されるタスクスケジューラで、OS側の複雑なスクリプトを不要にします。

### ステップ 1: 拡張機能の有効化

まず、データベースに拡張機能がインストールされ、有効になっていることを確認してください（`pg_cron` は通常、`postgresql.conf` の `shared_preload_libraries` での設定が必要です）。

```sql
CREATE EXTENSION IF NOT EXISTS pg_partman WITH SCHEMA partman;
CREATE EXTENSION IF NOT EXISTS pg_cron;

```

### ステップ 2: 管理設定 (pg_partman)

`CREATE TABLE` を使って手動でパーティションを作る代わりに、親テーブルの制御を `pg_partman` に委ねます。

以下の例では、`eventos` テーブルに対して月次のパーティションを自動作成するように設定しています：

```sql
SELECT partman.create_parent(
    p_parent_table => 'public.eventos',
    p_control      => 'data_evento',
    p_type         => 'native',    -- PGネイティブのパーティショニングを使用
    p_interval     => '1 month',   -- 1ヶ月ごとのパーティションを作成
    p_default      => 'true'       -- defaultテーブル（フォールバック用）を作成
    p_premake      => 2            -- 常に2ヶ月先の分まで作成しておく
);

```

これにより `pg_partman` は構造を理解しますが、勝手には動きません。新しいテーブルを作成すべき時期かどうかを確認するために、定期的に「呼び出す」必要があります。

### ステップ 3: メンテナンスのスケジュール設定 (pg_cron)

ここで `pg_cron` の出番です。Linuxの `crontab` を設定する代わりに、SQL経由で直接メンテナンスタスクをスケジュールします。

以下のコマンドは、`partman` のメンテナンス処理を1時間ごとに実行するように設定します：

```sql
-- run_maintenance() 関数を1時間ごとに実行するようにスケジュール
SELECT cron.schedule(
    'manutencao_particoes', -- ジョブ名
    '0 * * * *',            -- Cron式（毎時0分に実行）
    $$CALL partman.run_maintenance()$$
);

```

### 結果

この設定により：

1. 毎時間、`pg_cron` が起動し `run_maintenance()` を実行します。
2. `pg_partman` は、（`p_premake` で定義された）将来のパーティションが既に存在するか確認します。
3. 存在しない場合は自動的に作成され、新しいデータを挿入するためのテーブルがないという理由でアプリケーションが失敗することを防ぎます。
4. （オプション）設定されていれば、非常に古いパーティションの切り離しやアーカイブも自動的に行います。

このアーキテクチャにより、パーティショニングは「メンテナンスの頭痛の種」から「目に見えないパフォーマンスソリューション」へと変わります。
